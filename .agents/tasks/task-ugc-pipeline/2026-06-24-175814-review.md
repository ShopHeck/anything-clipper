# TikTok Shop URL-to-UGC-Video pipeline

A six-step pipeline that takes a TikTok Shop product URL, scrapes product data, generates a UGC script via LLM, produces TTS voiceover audio, gathers/generates visual assets, plans scenes against the voiceover timeline, and composes a final short-form vertical video using FFmpeg's complex filtergraph. The pipeline is orchestrated synchronously within a single 300-second serverless function invocation, updating a `ugc_projects` database row at each step so clients can poll for progress.

Watch for: TTS timing is estimated from character count rather than measured from the actual audio, meaning the video scene boundaries will drift from the voiceover on any text where speaking rate deviates from the 14 chars/sec constant (confirmed). The `/api/ugc/[id]/process` route exposes the full orchestration behind only a shared secret header, with no per-project status guard — a worker can re-trigger a completed or already-running project (confirmed). Scenes with no available asset produce an empty `imageUrl`, which will cause FFmpeg to fail at runtime since no fallback image is emitted (confirmed).

## High-level view

The pipeline is a linear chain with no parallelism: scrape → script → TTS → assets → scene plan → FFmpeg compose. Each step persists partial results to the database and advances the status column. If any step throws, the outer catch marks the project failed and returns an error, but the `markFailed` helper discards the error message — the string is accepted as a parameter and never written to the database.

Scene timing is derived entirely from character-count heuristics rather than from the actual TTS audio duration. The `scriptToAudio` function generates a single audio file from the concatenated script but calculates section boundaries using a fixed 14 chars/sec rate. The ASS captions and scene transitions are only approximately aligned to the actual voiceover — fast/slow passages will drift noticeably.

The worker auth path in the process route uses a shared secret but lacks both idempotency and status checks — a duplicate POST re-triggers the entire pipeline on an already-completed project.

The `ugc_projects` table stores presigned URLs (1-hour TTL) directly in JSONB columns. Any client polling the status endpoint after the TTL expires will receive broken links.

<details>
<summary>Issues (7)</summary>

1. **Estimated timing drift** — Section boundaries are calculated from character count (14 chars/sec) rather than extracted from the actual TTS audio. Captions and scene cuts will be noticeably out of sync on longer or shorter-than-average sections. Measure real audio duration per section or use the audio file's actual duration to proportionally adjust timings.
2. **Empty imageUrl crashes FFmpeg** — When no product images and no lifestyle images are available, `scene.assetUrl` is `undefined`, producing `imageUrl: ''` in the render spec. The compose step will try to download an empty URL and fail. Add a fallback placeholder image or abort the pipeline early.
3. **No re-entrance guard on process route** — A worker or user can POST to `/api/ugc/[id]/process` even if the project is already `composing` or `completed`, triggering a duplicate orchestration. Check `status` before proceeding.
4. **Error message stored nowhere** — `markFailed` updates the status to `'failed'` but discards the `error` string argument. Add an `error_message` column or store it in a JSONB field.
5. **Presigned URL expiry in DB** — TTS audio and asset URLs stored in `ugc_projects` are presigned with a 1-hour TTL. If the user polls the status endpoint hours later, they'll get expired links. Use storage keys and presign on read, or use long-lived URLs.
6. **300s timeout vs. pipeline length** — The process route sets `maxDuration = 300` but the pipeline makes 2+ LLM calls, 1 TTS call, up to 6 image downloads, 1 image generation call, and an FFmpeg render. Under normal load this may succeed, but any upstream latency spike will 504 the request. Consider an async worker architecture or at minimum log where time is spent.
7. **Product URL not validated for SSRF** — The `scrapeProduct` function passes the user-supplied URL directly to the scraping service without checking for internal/private addresses. If the scraping service is permissive, this could be used to probe internal infrastructure. Validate that the URL resolves to a public host, or trust the scraping service's own SSRF protections and document that assumption.

## Timing estimation vs. reality

The `scriptToAudio` function in `lib/tts/script-to-audio.ts` calls `generateTTS` with the full concatenated text as a single API call, then computes per-section timing using `estimateDuration`:

```typescript
const CHARS_PER_SECOND = 14;
export function estimateDuration(text: string, speed = 1.0): number {
  const charCount = text.trim().length;
  return charCount / (CHARS_PER_SECOND * speed);
}
```

The returned `timings` array drives both the scene plan (which images appear when) and the caption timing (word-level timestamps via `captionsFromScript`). The actual OpenAI TTS audio varies with content: a section full of numbers ("$24.99, 4.8 stars, 12,000 sold") is spoken much slower than 14 chars/sec; short exclamatory hooks are faster.

The mismatch manifests as: captions appearing before or after the words are spoken, and scene transitions happening during the wrong sentence. For a 30-second video, even a 1-2 second cumulative drift per section is jarring.

The fix is to either (a) generate TTS per-section and measure each segment's actual duration, or (b) use the OpenAI API's word-level timestamp response (available via the `timestamp_granularities` parameter on the transcription endpoint) to get real timing.

## Empty asset URL fallthrough

In `buildRenderSpec`, scenes are constructed from the scene plan:

```typescript
const scenes: UGCScene[] = scenePlan.map((scene, i) => ({
  imageUrl: scene.assetUrl || '',
}));
```

When `scene.assetUrl` is `undefined` (no images available), `imageUrl` becomes `''`. The `compose.ts` module then calls `downloadFile(spec.scenes[i].imageUrl, imgPath)` which will throw on `fetch('')` (invalid URL). This is caught by the outer try/catch and surfaces as a confusing "Failed to download" error rather than a clear "no assets available" message.

The pipeline should either require at least one image before entering composition, or provide a solid-color fallback frame generated locally.

## Process route lacks status guard and has a redundant query

The `/api/ugc/[id]/process` endpoint fetches the project but never checks `project.status`. A request can re-trigger orchestration on a project that is `completed`, `composing`, or already `failed`. This could produce duplicate storage writes or race conditions if two process calls run concurrently.

Additionally, the handler queries `ugc_projects` twice — once for auth verification (filtered by `user_id`) and again unconditionally for orchestration parameters. The second query should be eliminated in favor of reusing the first result.

## markFailed discards error detail

```typescript
async function markFailed(projectId: string, error: string): Promise<void> {
  await sql`UPDATE ugc_projects SET status = 'failed', updated_at = NOW() WHERE id = ${projectId}`;
}
```

The `error` parameter is accepted but never written. The status endpoint returns `status: 'failed'` with no diagnostic information. Either add an `error_message TEXT` column or store the error in the existing JSONB fields.

## SSRF surface in scrapeProduct

The orchestrator passes the user-supplied `url` directly to the scraping service:

```typescript
const scrapeRes = await fetch(`${base}/integrations/web-scraping/post`, {
  body: JSON.stringify({ url, getText: true }),
});
```

The `/api/ugc/create` route validates URL format (`new URL(url)`) but doesn't restrict it to public addresses. Whether this is exploitable depends on the scraping service's own network restrictions. If the service can reach internal hosts (metadata endpoints, internal APIs), an attacker could probe internal infrastructure. The risk is mitigated if the scraping service runs in an isolated network, but that assumption should be documented or enforced at this layer with a hostname allowlist or protocol check (reject non-http(s), reject private IP ranges).

## Leading silence gap

The scene planner's first scene starts at `timings[0].startSec`, which is always 0. However, if the first TTS section's estimated timing doesn't account for encoder silence (common in MP3 headers), and the actual audio has a brief silent lead-in, the first scene's zoompan begins slightly before the voiceover does. The `-shortest` flag on the output end handles trailing mismatches, but there's no equivalent guard at the start. A 100-200ms offset on `startSec` for the first scene would provide a buffer.
