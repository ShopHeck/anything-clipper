# OpenAI direct API fallback and UGC generation frontend

The change adds a direct OpenAI API path as a fallback when the project proxy (NEXT_PUBLIC_CREATE_BASE_URL / ANYTHING_PROJECT_TOKEN) is not configured. This applies to three integration points: chat completions, DALL-E image generation, and product scraping. It also introduces a full UGC generation page (`/ugc`) with form inputs, progress polling, and script preview, plus a dashboard link to reach it.

Watch for: The scraping fallback does a raw `fetch()` to the user-supplied URL from the server, inheriting the previous SSRF concern but now executing it directly from the app server rather than delegating to an isolated scraping service (confirmed). The "fire and forget" pattern for kicking off the process endpoint means a network failure on that POST silently drops the job — the user sees "UGC generation started!" but nothing ever runs, and there's no recovery path (confirmed). The `OPENAI_MODEL` env var controls the chat model but DALL-E is hardcoded to `dall-e-3` with no override (confirmed).

## High-level view

The AI gateway (`ai.ts`) now routes proxy-first, then direct OpenAI, correctly mapping the proxy's custom `json_schema` body field to OpenAI's `response_format.json_schema` structure on the direct path. The `strict: true` flag on the direct path means all schemas must have `additionalProperties: false` set recursively — the `product_details` schema in `orchestrate.ts` should be verified against this constraint or it will produce 400 errors.

The scraping fallback replaces the dedicated scraping proxy with a direct HTTP fetch and regex-based HTML stripping. This works for SSR pages but will produce poor extraction quality on JavaScript-rendered pages (TikTok Shop is heavily JS-dependent), and it opens the server to SSRF since the URL now hits the network directly from the app process.

The UGC frontend depends on three existing API endpoints and uses react-query for poll-based progress tracking. The "fire and forget" fetch to the process endpoint is the critical reliability gap — if it fails, the job is stuck in its initial status forever with no user-facing signal.

<summary>Issues (4)</summary>

1. **Fire-and-forget process kick-off** — The UGC page fires `fetch(/api/ugc/${id}/process)` without awaiting or checking the response. If that POST fails, the job is created but never processed, and the user sees a spinner forever (the `.catch` only logs to console). Await the response and surface failures, or add a client-side staleness check that shows a retry prompt if status doesn't advance within 30 seconds.
2. **Direct-fetch SSRF on scrapeProduct** — With the direct fallback, the app server itself fetches user-supplied URLs. No hostname validation prevents requests to `http://169.254.169.254/` or internal services. Add a URL allowlist (public hosts only, http/https only) or restrict via DNS resolution check before fetching.
3. **JS-rendered pages return empty/garbage content** — The direct fetch fallback gets raw HTML. TikTok Shop renders product data via JavaScript hydration. The regex HTML-stripping will yield boilerplate text on these pages, causing either a pipeline failure or hallucinated extraction. Direct fetch only works reliably on SSR pages (Shopify, Amazon). Document or detect this.
4. **No image model override** — `OPENAI_MODEL` controls chat completions but DALL-E 3 is hardcoded with no equivalent env var. Add `OPENAI_IMAGE_MODEL` if model flexibility is needed (e.g., for gpt-image-1 or future models).

## Direct-fetch SSRF surface in scrapeProduct

The prior review flagged SSRF when the user-supplied URL was forwarded to the proxy scraping service. That concern was partially mitigated by the proxy's network isolation. The new fallback removes that layer of defense:

```typescript
} else if (openaiKey) {
  const scrapeRes = await fetch(url, {
    headers: {
      'User-Agent': 'Mozilla/5.0 ...',
    },
  });
```

The app server process now makes an outbound HTTP request to whatever the user provides. The `/api/ugc/create` route validates `new URL(url)` (format check) but that permits `http://169.254.169.254/latest/meta-data/` on cloud hosts, `http://localhost:3000/api/internal/...`, or any RFC-1918 address.

Since this path is gated on `OPENAI_API_KEY` being set (production config), it's always active in deployments that lack the proxy. A pre-fetch DNS resolution check rejecting private/link-local ranges, or a protocol+hostname allowlist, would close the gap.

## Fire-and-forget reliability hole

In `page.tsx`, after the create call succeeds:

```typescript
fetch(`/api/ugc/${newJobId}/process`, {
  method: 'POST',
  ...
}).catch((err) => {
  console.error('Process kick-off failed:', err);
});
```

The user receives `toast.success('UGC generation started!')` and the polling loop activates. If the process POST fails (serverless cold start timeout, 502, or browser navigation before completion), the job row stays in its initial status indefinitely.

The polling loop refetches every 2.5 seconds with no upper bound on retries or staleness detection. A simple fix: await the process call and treat failure as a submission error, or add a client-side staleness check that surfaces a retry option if the status hasn't advanced within 30 seconds.

## HTML stripping quality on JS-rendered pages

The fallback scraper uses:

```typescript
pageText = html.replace(/<[^>]*>/g, ' ').replace(/\s+/g, ' ').trim();
```

On TikTok Shop (the primary target), product name and features are injected via JavaScript hydration and won't appear in the initial HTML response. The resulting `pageText` will be mostly navigation chrome and script tag content.

The test mocks a clean HTML body (`<h1>Test Product</h1><p>Great item</p>`) which passes, but doesn't represent actual TikTok Shop responses. In practice, `pageText` will be non-empty but useless, and the LLM extraction will either hallucinate product details or fail. Direct fetch only works on SSR pages (Shopify, Amazon), not client-rendered SPAs like TikTok Shop.

## strict: true schema constraint

The direct OpenAI path adds `strict: true` to the json_schema response format. This requires all schema objects to have `additionalProperties: false` set recursively. The `product_details` schema in `orchestrate.ts` should be checked for this — if any nested object lacks this property, the direct API will return a 400 error that surfaces as `AiUnavailableError('upstream returned 400')` with no diagnostic detail about which schema property violated the constraint.
